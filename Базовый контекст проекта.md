Разрабатываем концепт Terminal Workspace — terminal-first TUI для быстрого доступа к рутинным рабочим источникам информации и действиям над ними.

Ключевая продуктовая ценность: уменьшить переключение между терминалом, браузером, GitHub, IDE, заметками, CI и другими инструментами.

Основная модель

Core
↓
Installed Plugins
↓
Workspace
↓
Active Plugins
↓
Groups
↓
Items
↓
Actions

Workspace

Workspace = конкретный проект.

Примеры:

~/projects/bookwriter.nvim
~/projects/soruar
~/projects/lightning-game

Workspace хранит project-local configuration и выбирает, какие из глобально установленных plugins активны.

Plugin

Plugin — workspace-agnostic функциональное расширение.

Примеры:

- Git
- GitHub
- Files
- Writing
- Godot
- Blender
- AI

Нельзя делать project-specific plugins вроде SoruarPlugin.

Например один Writing Plugin должен работать с любым литературным проектом.

Plugin может предоставлять

- Groups
- Items
- Actions
- Commands
- Context providers
- Keybindings
- Background jobs
- Events/status

Пример:

GitHub
├── Pull Requests
├── Issues
├── Builds
├── Actions
├── Releases
└── Gists

Внутри Builds находятся реальные build items, а после выбора build доступны его native actions: logs, rerun, cancel, open и т. д.

Состояния plugin

Нужно различать:

installed globally
workspace enabled
session enabled
available
connected

Пользователь может:

- включить plugin;
- отключить для workspace;
- временно отключить до конца сессии;
- удалить plugin.

disable != uninstall.

Custom plugins

Поддержка пользовательских plugins — архитектурное требование с первой версии.

First-party plugins должны использовать тот же основной Plugin API, что и custom plugins.

Core должен оставаться минимальным и не содержать domain-specific логики Git/GitHub/Writing/Godot и т. п.

UX

Keyboard-first TUI.

Основной flow:

Plugin
↓
Group
↓
Item
↓
Action

Не нужно искусственно приводить PR, branch, note и build к пользовательской сущности вроде WorkItem. Они сохраняют семантику исходного инструмента.

AI

AI не является центром продукта.

Terminal Workspace должен быть полезен без AI.

Позже AI можно реализовать:

- как отдельный Plugin;
- как дополнительные actions других plugins;
- как context consumer через provide_context().

Hybrid AI является потенциальным нижележащим механизмом, но не входит в основную продуктовую гипотезу MVP.

MVP

Проверяемая гипотеза:

Может ли единый plugin-based terminal UI существенно сократить ежедневное переключение между приложениями?

Первые plugins:

- Files
- Git
- GitHub
- один независимый custom plugin для проверки расширяемости.

Не включать в MVP:

- сложную agent orchestration;
- RAG;
- собственный task manager;
- универсальный WorkItem;
- AI-generated tabs;
- marketplace;
- GUI.

Последний подготовленный артефакт: полноценный PRD и архитектурный концепт Terminal Workspace.
