# Terminal Workspace — roadmap до MVP

Обновлено: 4 октября 2026.

План опирается на [AGENTS.md](AGENTS.md), [контекст проекта](Базовый%20контекст%20проекта.md) и [Draft требований](Базовые%20продуктовые%20требования.md). Порядок этапов и критерии ниже — рабочий план реализации, который можно корректировать. Конкретные crates, runtime, формат конфигурации, протокол и модель процесса плагинов выбираются отдельно и фиксируются в `docs/decisions/`.

Цель MVP: полезная без AI терминальная рабочая среда для одного локального проекта с Files, Git, GitHub и независимо устанавливаемым custom plugin. Каждый этап должен оставлять работающий сквозной сценарий.

## Что уже работает

- [x] Открытие Workspace по локальному пути при запуске и переключение проектов в одной сессии.
- [x] Восстановление контекста проекта в сессии и независимые настройки, разрешения и временное отключение.
- [x] Локальные bindings активного плагина без namespace, области Plugin/Group/View и project-local overrides; подсказки продолжений и диагностика конфликтов.
- [x] Files: список каталогов, вложенная навигация, возврат, фильтр, сортировка, refresh и предпросмотр файла.
- [x] Путь Plugin → Group → Item → Action с клавиатуры.
- [x] Общий маршрут команд плагина из multi-key bindings, `:commands`, палитры и contextual Actions.
- [x] Blocks для результатов команд и отдельный результат Navigation для переходов.
- [x] Сохранение фильтра, порядка и выбора при возвращении в каталог в пределах сессии.
- [x] Компактный TUI и оформление по референсу: две области, рамки, цвета и подсказки клавиш.
- [x] Раздельные Workspace/session activation в API ядра.
- [x] Project-local конфигурация, сохранение разрешений и Core-команды активации в TUI.
- [x] Базовая проверка выданного `WorkspaceRead` и обработка ряда ошибок/panic плагина.
- [x] Отдельно упакованный Rust custom plugin и проверка его работы в двух Workspaces.
- [x] Проверки командных маршрутов, Unicode, границ кадра, навигации, PTY, resize и восстановления терминала.

Это прототип, а не законченный MVP. Настройки и разрешения сохраняются в project-local JSON; плагин связывается с Core при сборке, разрешения не изолируют недоверенный код. Глобальная установка и runtime-загрузка отсутствуют. Git, GitHub и асинхронное обновление не реализованы. Целевые показатели производительности не подтверждены.

## 1. Настройки Workspace и управление активацией — выполнено

Сценарий: пользователь выбирает активные плагины для проекта, временно отключает один из них и после перезапуска получает ожидаемое состояние.

- [x] Сохранять project-local конфигурацию: активные плагины, plugin-specific настройки и локальные overrides.
- [x] Сохранять решения о разрешениях; позволять просматривать и отзывать их. На этом этапе речь о доступной модели `WorkspaceRead`, а не о готовой изоляции.
- [x] Добавить Core-команды управления активацией через общий CommandRegistry. Команда может работать без выбранного Item и без активного плагина.
- [x] Вывести в TUI постоянное и временное отключение, повторное включение и понятные состояния.
- [x] Обработать отсутствие активных плагинов, неизвестные записи конфигурации, ошибки чтения и сохранения без потери работающего интерфейса.
- [x] Выбрать формат, путь хранения и правила версионирования конфигурации; документировать как техническое решение.

Готово, когда: постоянное отключение переживает перезапуск; временное отключение заканчивается с сессией; установленный плагин и его настройки сохраняются; два проекта имеют независимые настройки. Операции доступны с клавиатуры и проходят общий командный маршрут.

Проверено: restart, независимость двух проектов, четыре маршрута команд, повреждённая конфигурация и отказ сохранения, custom plugin с разными settings в двух проектах, PTY. JSON v1 и исходный Plugin API v0.2 описаны в [решении реализации](docs/decisions/0003-workspace-configuration.md). Settings редактируются вручную; применение сохранённых overrides во вводе реализовано в этапе 2.

Граница: конфигурация, разрешения и активация относятся к Core; трактовка plugin-specific настроек остаётся у плагина.

## 2. Переключение Workspace и расширяемый ввод — выполнено

Сценарий: пользователь переключает проект без выхода из приложения; тот же плагин получает новый Workspace и работает с его данными и настройками.

- [x] Открывать и переключать Workspace через Core-команды, палитру и клавиатуру.
- [x] Восстанавливать подходящее состояние интерфейса для проекта; не переносить выбор, данные и разрешения другого Workspace.
- [x] При неудачном открытии оставлять текущий Workspace доступным.
- [x] Обобщить multi-key ввод: последовательности произвольной поддерживаемой длины, отмена, обнаружение продолжений и конфликтов.
- [x] Поддержать объявления bindings плагинами и project-local overrides вместо Files-специфичного списка в UI.
- [x] В контексте активного плагина вызывать его локальные bindings без клавиши namespace: контекст плагина уже известен. Плагин объявляет область действия binding — плагин, группа или представление. В этапе 2 Files сохранял прежние последовательности с префиксом как локальные aliases; итерация 2.1 убирает их из defaults; глобальный вызов другого плагина пока не реализован и не закреплён как требование.
- [x] Сохранить leader преимущественно для глобальных команд Core/Workspace. В режиме ввода текста локальные bindings не срабатывают. Явный project-local override имеет приоритет; неоднозначные конфликты bindings показываются при загрузке конфигурации.
- [x] Проверить согласованность CommandId для bindings, `:commands`, палитры и Actions после переключения проекта.

Готово, когда: Files и custom plugin работают при переключении между двумя проектами; ошибки нового проекта не закрывают старый; команды и bindings используют контекст текущего Workspace. Локальные bindings активного плагина работают без его префикса и вызывают те же CommandId, что `:commands`, палитра и Actions; ввод текста и конфликты проверены. Раскладка клавиш остаётся изменяемым default.

Граница: Workspace, ввод и маршрутизация относятся к Core; доменные переходы и контекстные действия задаёт плагин.

Проверено: Files и независимо упакованный Catalog в двух проектах одного App; четыре маршрута команд; независимость activation/permissions/settings, suspend при возврате, свежая загрузка данных и восстановление вложенной локации, выбора, фильтра и порядка. Ошибки пути, конфигурации и сохранения defaults оставляют текущий проект доступным. Scoped bindings/overrides, отмена, Unicode, конфликты, ввод текста и PTY проверены. API v0.3 и технические решения описаны в [решении этапа 2](docs/decisions/0004-workspace-switching-and-bindings.md). UI-состояние живёт в пределах сессии; bindings пока поддерживают печатные символы без пробелов. Performance-цели MVP не подтверждены.

## 2.1. Согласование раскладки с Neovim-подобной грамматикой — выполнено

Порядок: после этапа 2, до внедрения defaults Git в этапе 4. Это отдельная небольшая итерация; она не блокирует архитектурную работу этапа 3.

Сценарий: пользователь применяет общую грамматику навигации во всех плагинах, а локальные операции вызывает без namespace активного плагина.

- [x] Сохранить `h/j/k/l` и Enter для навигации и открытия/default Action; `h` или Backspace — для родительского контекста там, где он доступен.
- [x] Сохранить `/` для поиска/фильтра, `:` для команд, Space для палитры и Esc для отмены/возврата. Leader использовать преимущественно для глобальных операций Core/Workspace.
- [x] Пересмотреть defaults Files: оставить локальный `p` для preview; убрать `o/u/y` и aliases `fp/fs/fo/fu`. Открытие и переход к родителю доступны через общую навигацию; показ пути — через contextual Actions, палитру и `:files.path`.
- [x] Сохранить настраиваемые bindings и локальные области Plugin/Group/View. Не требовать отдельной клавиши для каждой операции; не возвращать обязательный префикс активного плагина.
- [x] Проверить defaults custom plugin на согласованность с общей грамматикой; обновить справку, README, техническое решение и тесты. Удаление aliases касается defaults, а не запрета таких пользовательских overrides.
- [x] Пройти keyboard-only сценарии Files и custom plugin, включая все маршруты команд, переключение Workspace, ввод текста, подсказки и конфликты overrides; повторить PTY-проверку.

Готово, когда: Files использует согласованные defaults без дублирующих `o/u/y` и прежнего namespace-префикса; все операции остаются discoverable и используют прежние CommandId/маршруты. Изменение не добавляет копирование, undo или другие новые доменные операции ради соответствия клавишам Neovim. Конкретная раскладка остаётся изменяемым default прототипа.

Граница: общая грамматика ввода и навигация относятся к Core; локальные bindings и contextual Actions объявляют плагины через основной API.

Проверено: 35 Rust-тестов Core/Files/TUI и 3 теста независимо упакованного Catalog; fmt и clippy для обоих пакетов; Unix PTY с `p`, навигацией `l/h`, Actions/палитрой/командной строкой для показа пути, переключением Workspace и восстановлением терминала. Явный override `fp` продолжает работать; scoped overrides, конфликты и Unicode проверены. Актуальные defaults и границы изменения описаны в [решении итерации 2.1](docs/decisions/0005-keyboard-defaults.md). Performance-цели MVP остаются задачей этапа 7.

## 3. Установка, runtime и разрешения custom plugins — следующий архитектурный этап

Сценарий: пользователь устанавливает отдельно упакованный плагин и подключает его к нескольким проектам без пересборки приложения.

- [ ] Выбрать минимальную модель упаковки, discovery, исполнения и совместимости; зафиксировать решение до расширения API.
- [ ] Реализовать глобальную установку, обнаружение, загрузку и отдельный uninstall. Workspace не содержит код плагина.
- [ ] First-party и custom plugins используют одинаковый или максимально близкий основной публичный API.
- [ ] Разделить installation, Workspace activation, session activation, availability и connection в состоянии и отображении.
- [ ] Реализовать lifecycle: запуск, остановка активности, освобождение ресурсов, обработка ошибок запуска/исполнения.
- [ ] Расширить permission model на файлы, процессы, сеть, credentials и environment с явными границами доступа.
- [ ] Определить, какие ограничения действительно enforced выбранным runtime; проверить отказы и документировать оставшиеся ограничения.
- [ ] Документировать и версионировать внешний контракт и обновить пример custom plugin под реальную установку.

Готово, когда: независимо упакованный custom plugin устанавливается, загружается и работает в двух Workspaces; отключение останавливает его текущую активность; сбой плагина оставляет Files и навигацию доступными; несовместимость версии и отказ в разрешении объясняются пользователю. Uninstall отделён от отключения. Недоверенный код не объявляется изолированным без проверки enforcement.

Граница: установка, runtime, события и permissions относятся к Core; реализация функциональной области — к пакету плагина.

## 4. Git как локальный плагин

Сценарий: пользователь видит состояние репозитория, выбирает изменённый файл или ветку и вызывает действие, оставаясь в терминале.

- [ ] Реализовать минимальные стабильные Groups для статуса и веток, включая пустые состояния.
- [ ] Показывать нативные Git-объекты; не вводить универсальный WorkItem.
- [ ] Добавить просмотр diff и необходимые простые действия; конкретный набор изменяющих операций определить при реализации.
- [ ] Провести команды через основной Plugin API и общую маршрутизацию.
- [ ] Обработать отсутствие репозитория, ошибки Git и отказ в необходимых разрешениях.

Готово, когда: локальный путь Git проходит Group → Item → Action с клавиатуры в двух репозиториях, работает offline и не нарушает Files при ошибке. Выбранные изменяющие операции проверены на временном репозитории; результаты представлены через Blocks там, где это полезно.

Граница: вся Git-логика живёт в плагине. Способ вызова Git — отдельное техническое решение, а не требование использовать конкретную библиотеку или процесс.

## 5. Неблокирующие задачи, кэш и обновления

Сценарий: медленный плагин обновляет данные, пока пользователь продолжает навигацию и работу с локальными файлами.

- [ ] Добавить общий механизм фоновых задач и доставки результатов без блокировки TUI.
- [ ] Поддержать объявляемые плагином стратегии refresh: вручную, при фокусе, по интервалу или событию, когда это требуется.
- [ ] Показать состояния загрузки, устаревшего кэша, ошибки и недоступности.
- [ ] Показывать имеющийся кэш сразу и обновлять его в фоне.
- [ ] Отменять задачи при отключении плагина и переключении Workspace; не применять результаты старого контекста.
- [ ] Проверить зависшие задачи, повторный refresh, сбои и сохранение выбора после обновления.

Готово, когда: искусственно медленный или ошибающийся плагин не блокирует клавиатурную навигацию и Files; старые результаты не попадают в другой Workspace; отключение прекращает активность; пользователь понимает, свежие ли данные он видит.

Граница: задачи, отмена, хранение и события — механизмы Core; стратегия обновления, доменный кэш и трактовка ошибок — ответственность плагина. Async runtime выбирается по задаче отдельно.

## 6. GitHub как сетевой плагин

Сценарий: пользователь открывает PR проекта, читает сведения и вызывает контекстное действие; при отсутствии сети продолжает работать с локальными данными.

- [ ] Реализовать минимальные группы PR и Issues с нативными объектами и контекстными действиями.
- [ ] Настраивать связь с репозиторием и авторизацию плагина через публичные контракты.
- [ ] Использовать разрешения на сеть и credentials, не сохранять секреты в project-local конфигурации.
- [ ] Применить фоновую загрузку и кэш из этапа 5.
- [ ] Обработать отсутствие авторизации, отказ доступа, offline, лимиты и ошибки сервиса.
- [ ] Выбрать небольшой набор простых действий и проверить их общий командный маршрут.

Готово, когда: GitHub подключается по явному решению пользователя; кэш отображается сразу; медленная сеть и отказ авторизации не мешают Files/Git; действия доступны с клавиатуры и имеют одинаковый смысл через все способы вызова.

Граница: GitHub API, PR, Issues и авторизация интеграции относятся к плагину; Core предоставляет транспортные механизмы, runtime и permissions без GitHub-специфичных веток.

## 7. Проверка и выпуск MVP

- [ ] Пройти сквозной сценарий: открыть/переключить проект → установить и настроить плагин → включить → выбрать группу и объект → выполнить действие → отключить временно/постоянно.
- [ ] Повторить сценарий с Files, Git, GitHub и custom plugin; проверить пустые группы и отсутствие активных плагинов.
- [ ] Проверить ошибки плагина, offline, отзыв разрешений, перезапуск и переключение Workspace во время задачи.
- [ ] Измерить startup без сетевых плагинов (< 300 ms), открытие локальной группы (< 100 ms) и воспринимаемую задержку навигации (< 16–50 ms).
- [ ] Зафиксировать методику измерений, условия, результаты и ограничения; отдельно проверить мгновенное отображение доступного кэша сетевой группы. Единичный PTY smoke check не подтверждает все performance цели.
- [ ] Проверить keyboard-only UX, обнаружение действий, resize и восстановление терминала на macOS/Linux.
- [ ] Обновить инструкции установки, конфигурации, управления разрешениями и разработки custom plugins.
- [ ] Устранить блокирующие дефекты и явно перечислить ограничения первого релиза.

Готово, когда: P0 из AGENTS.md подтверждён проверками, приложение полезно без AI, публичный Plugin API соответствует реальной реализации, а ограничения доступа описаны без обещаний отсутствующей защиты.

## После MVP

Writing из визуального референса — возможный следующий плагин, не обязательная интеграция MVP. Он должен работать с разными писательскими проектами; данные конкретной книги не входят в Core. Дальнейший набор функций выбирается после проверки основной гипотезы приложения.

AI остаётся optional. Marketplace, облачная синхронизация, совместная работа, универсальный task manager/WorkItem, RAG и сложная agent orchestration не входят в этот roadmap до MVP.

## Как поддерживать план

После этапа обновлять checklist, описывать реально проверенное и оставшиеся ограничения. При изменении публичного API повторять проверку независимо упакованного custom plugin в нескольких Workspaces. Новые технические решения записывать в `docs/decisions/`; новые продуктовые обязательства принимать отдельно.
