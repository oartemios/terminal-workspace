# Terminal Workspace — инструкции для coding agents

## Статус и источники решений

Этот файл задаёт принятые продуктовые и архитектурные ограничения для локальной разработки Terminal Workspace. Основание: «Базовый контекст проекта.txt», «Базовые продуктовые требования.txt» (Draft v0.1) и явно принятые пользователем решения в беседе «Собрать инфографику», включая уточнения в запросе на этот файл. Примеры команд, клавиш, API и экранов в исходных материалах иллюстрируют принцип; не считай их утверждёнными точными контрактами, если это отдельно не указано.

Если новое решение не следует из этих источников, выбирай обратимый вариант и фиксируй его как решение реализации, а не как принятое требование. Не закрепляй без отдельного решения конкретные Rust crates, TUI framework, async runtime, формат сериализации, ABI, модель процесса плагина или структуру каталогов.

## Цель и неизменные принципы

- Terminal Workspace — terminal-first, keyboard-first TUI для доступа к частой рабочей информации и простым действиям в пределах проекта. Главная гипотеза MVP: единый интерфейс сокращает переключение между терминалом, браузером, IDE, GitHub и другими инструментами. Приложение должно быть полезным без AI.
- Основной язык реализации — Rust. Neovim служит ориентиром для взаимодействия, Warp — для структурированного представления информации и результатов команд. Не копируй GUI-подобные визуальные паттерны Warp или буквальную внутреннюю модель Neovim.
- Workspace соответствует конкретному локальному проекту. Он хранит project-local настройки и выбирает активные глобально установленные плагины. Реализация плагина не принадлежит Workspace.
- Plugin реализует функциональную область и остаётся workspace-agnostic. Git, GitHub, Files, Writing и прочая предметная логика живут в плагинах; не создавай плагины, привязанные к одной книге, игре или репозиторию.
- Core минимален и domain-agnostic: TUI, навигация, ввод и команды, plugin runtime/lifecycle, Workspace, конфигурация, события, разрешения, состояние сессии, локальное хранение и примитивы рендера. Не переноси предметную логику в Core ради удобства одного плагина.
- Custom plugins — архитектурное требование первого релиза. First-party и пользовательские плагины используют одинаковый или максимально близкий основной Plugin API; не добавляй скрытый привилегированный путь для встроенных интеграций.
- Сохраняй plugin-native семантику: PR остаётся PR, branch — branch, note — note. Технический интерфейс Item допустим, но не вводи универсальную пользовательскую сущность WorkItem.

## Архитектурные инварианты

- Основной пользовательский путь: Workspace → Plugin → Group → Item → Action. Group — стабильная область плагина, существующая и при нуле элементов. Item — объект плагина и группы; допустимые действия определяются его контекстом.
- Различай Command и contextual Action. Command — адресуемая операция Core или плагина, доступная через разные способы вызова. Action — допустимое действие для текущего Item или контекста; оно может приводить к вызову команды с нужными аргументами. Не своди все действия к бесконтекстным строкам и не заставляй все команды иметь выбранный Item.
- Используй единый CommandRegistry: multi-key bindings, :commands, command palette и contextual Actions должны сходиться к общим CommandId / CommandInvocation, когда выполняют одну операцию. Не реализуй отдельную бизнес-логику для каждого способа вызова. Конкретная Rust-форма этих контрактов пока не утверждена.
- Block — структурированный результат выполнения команды, если результату нужны источник, состояние, содержимое или доступные операции. Это не универсальная модель всех данных плагинов и не замена Item.
- Buffer обозначает рабочий контекст с содержимым и состоянием; View — способ его размещения/отображения. Не превращай эти понятия в обязательную копию buffer/window/tabpage Neovim и не предписывай каждому плагину одинаковую сетку.
- Плагин может предоставлять Groups, Items, Actions, Commands, context providers, keybindings, фоновые задачи, события и статус. Не требуй все возможности от каждого плагина.
- Различай состояние установки, включение для Workspace, включение в сессии, доступность и подключение. Отключение на сессию прекращает текущую активность, но не меняет конфигурацию Workspace; постоянное отключение не удаляет установку и настройки. Uninstall — отдельная операция.
- Ошибка одного плагина не завершает Workspace. Медленная сеть не блокирует навигацию; локальные сценарии продолжают работать offline. Показывай понятное состояние недоступности или ошибки.
- Пользовательские плагины не считай доверенными по умолчанию. Архитектура должна учитывать разрешения на файлы, процессы, сеть, credentials и environment. Не утверждай, что изоляция или enforcement уже существуют, если реализация их не обеспечивает.

## UX и правила ввода

- Проектируй реальный терминальный интерфейс, а не GUI, нарисованный символами. Не добавляй кнопки и иконки действий вроде + для создания заметки; операции вызываются с клавиатуры и доступны для обнаружения в контексте.
- Основная композиция: вкладки плагинов сверху; ниже — локальные группы или подвкладки активного плагина; затем рабочая область. Используй terminal-native statusline и overlays для режима, контекста, команд и доступных действий. Рабочая область сохраняет свободу представления данных конкретного плагина.
- Поддерживай keyboard-only путь Plugin → Group → Item → Action, быстрые переходы, возврат, поиск, фильтрацию, сортировку и refresh там, где это применимо. Действия над текущим объектом должны быть discoverable.
- Multi-key grammar: первая клавиша может обозначать namespace плагина, последующие — мнемоническое действие или объект. Leader зарезервирован преимущественно для глобальных действий Core/Workspace. Не фиксируй примеры g s, w n или конкретную leader-клавишу как обязательные defaults без отдельного решения.
- Поддерживай :commands и command palette как пути к зарегистрированным командам. Одна операция, вызванная сочетанием клавиш, командной строкой или палитрой, должна иметь общий смысл и результат. Контекстные Actions используют тот же маршрут исполнения, когда обращаются к той же операции.
- Показывай structured output через Blocks там, где это помогает читать, выбирать и повторно использовать результаты. Blocks не должны подменять списки и объекты плагина.

## Границы плагинов и Workspace

- Workspace задаёт root, project-local и plugin-specific настройки, активные плагины, состояние интерфейса и локальные overrides; не содержит код плагинов. Один плагин работает с разными Workspaces без project-specific веток.
- Разделяй global installation, workspace activation и session activation. Обнаружение применимости плагина не должно само включать его, кроме явно разрешённых defaults.
- Плагины могут объявлять подходящую стратегию обновления: вручную, при фокусе, по интервалу или по событию. Сетевые данные обновляй без блокировки TUI; при наличии кэша показывай его сразу.
- Core предоставляет общие механизмы конфигурации, событий и permissions. Плагин получает контекст текущего Workspace через общий контракт, а не через доступ к скрытым внутренним данным Core.
- AI остаётся optional: позже он может быть отдельным плагином, дополнительными действиями или потребителем контекста других плагинов. Основные сценарии не зависят от AI.

## MVP и исключения

- P0: открыть/переключить Workspace; установить, обнаружить, загрузить и настроить плагин; включить его для Workspace, отключить постоянно или до конца сессии; пройти Group → Item → Action с клавиатуры; иметь multi-key ввод, :commands и command palette; обеспечить базовую permission model и локализацию ошибок плагина.
- Первые интеграции: Files, Git и GitHub. Добавь как минимум один независимо упакованный custom plugin вне first-party дерева, чтобы проверить основной API. Writing подходит как пример, но не является обязательным выбранным плагином MVP.
- Вне MVP: собственный task manager, универсальный WorkItem, автоматическое объединение сущностей плагинов, сложная AI/agent orchestration, RAG, marketplace, GUI, облачная синхронизация, совместная работа, сложные dashboards и AI-generated tabs.
- Целевые показатели из Draft v0.1: startup без сетевых плагинов < 300 ms, открытие локальной группы < 100 ms, воспринимаемая задержка навигации < 16–50 ms; сетевые группы должны сразу показывать кэшированное состояние и обновляться асинхронно. Измеряй показатели, не объявляй их достигнутыми без проверки.

## Рабочие правила для агента

Все новые изменения выполняй в отдельной тематической ветке и отправляй через Pull Request в `main`. Не коммить и не делай push напрямую в `main`; merge PR выполняй только по явному запросу пользователя. Перед созданием PR выполни относящиеся к изменению проверки и укажи их результат.

1. Перед значимым изменением определи пользовательский сценарий, границу Core/Plugin, способ вызова операции и проверку результата. Сохраняй работающий сквозной путь вместо большой пустой заготовки.
2. При добавлении команды проверь, имеют ли keybinding, :command, palette и contextual Action один CommandId/маршрут исполнения там, где это одна операция. При добавлении Block проверь, что он описывает output, а не маскирует доменный Item.
3. При расширении Plugin API проверь независимо упакованный custom plugin и работу того же плагина в нескольких Workspaces. Документируй и версионируй публичный контракт, когда он становится внешним.
4. При изменении TUI проверь полный keyboard-only сценарий, обнаружение действий, размещение вкладок/групп/рабочей области и отсутствие GUI-подобных кнопок. Не выдавай иллюстративные hotkeys за утверждённую раскладку.
5. Проверяй состояния плагинов, отключение на сессию и для Workspace, offline/ошибки и относящиеся к изменению performance цели. Сообщай, что реально проверено и какие ограничения остались.
6. Если реализация требует выбора crate, runtime, формата, ABI или layout репозитория, принимай решение отдельно на основании задачи и фиксируй его как локальное техническое решение, а не как исходное продуктовое требование.

## Checklist перед завершением изменения

- Сохраняется ли terminal-first, keyboard-first UX без GUI-подобных операций?
- Сохраняется ли native смысл объектов и проходит ли действие через общий командный маршрут?
- Не вырос ли Core за счёт логики конкретной области?
- Может ли custom plugin сделать то же через доступный основной API?
- Различаются ли installation, Workspace/session activation, availability и connection?
- Работает ли локальный путь при проблемах сети и ошибке другого плагина?
- Не превращено ли примерное или неподтверждённое решение в обязательный контракт?
