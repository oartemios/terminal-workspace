Terminal Workspace

Product Requirements & Architecture Concept

Статус: Draft v0.1
Тип продукта: Terminal-first workspace / TUI
Основная платформа MVP: macOS / Linux terminal
Ключевой принцип: информация и повседневные рабочие действия должны быть доступны из одного терминального интерфейса без постоянного переключения между приложениями.

⸻

1. Product Summary

Terminal Workspace — расширяемая терминальная рабочая среда, которая агрегирует часто используемые источники рабочей информации и действия над ними.

Примеры:

- Git;
- GitHub;
- локальные файлы;
- Markdown/Obsidian;
- AI-сессии;
- CI/build systems;
- Godot;
- Blender;
- специализированные инструменты для писательства;
- пользовательские интеграции.

Каждая интеграция реализуется как Plugin.

Плагин:

1. подключается к определённому инструменту или функциональной области;
2. предоставляет набор логических групп;
3. отображает элементы внутри групп;
4. предоставляет действия над элементами;
5. при необходимости добавляет команды, context providers и фоновые операции.

Пример:

GitHub
├── Pull Requests
├── Issues
├── Builds
├── Actions
├── Releases
└── Gists

Terminal Workspace не пытается заменить GitHub, Obsidian, Blender или другие системы.

Его задача — сделать наиболее частые операции доступными непосредственно из терминала.

⸻

2. Product Thesis

Пользователь регулярно переключается между:

terminal
browser
GitHub
IDE
Obsidian
AI client
CI
file manager
other tools

Значительная часть этих переключений нужна только для получения небольшой порции информации или выполнения простого действия:

проверить build
посмотреть PR
найти issue
посмотреть diff
открыть заметку
проверить branch
посмотреть состояние агента
прочитать лог

Terminal Workspace переносит такие операции туда, где пользователь уже работает — в терминал.

Основная формула продукта:

Информация → выбор объекта → действие

а не:

приложение → навигация → экран → объект → действие.

⸻

3. Основная ценность

Продукт должен уменьшать:

- context switching;
- количество открываемых приложений;
- навигацию по web-интерфейсам;
- повторяющийся поиск рабочей информации;
- ручную передачу контекста между инструментами.

При этом Terminal Workspace не должен превращаться в:

- новую IDE;
- новую систему управления задачами;
- универсальную базу данных;
- AI-чат с дополнительными кнопками;
- попытку абстрагировать все внешние сервисы в одну универсальную сущность.

⸻

5. Core

Core — минимальное ядро приложения.

Core не должен знать специфики:

Git
GitHub
Writing
Godot
Blender
Obsidian
AI

Эта функциональность реализуется плагинами.

Core отвечает за:

- TUI;
- plugin runtime;
- workspace lifecycle;
- navigation;
- command palette;
- keybindings;
- configuration;
- events;
- permissions;
- plugin lifecycle;
- local persistence;
- rendering primitives;
- session state.

⸻

6. Plugin

Plugin — универсальное workspace-agnostic расширение Terminal Workspace.

Плагин не принадлежит проекту.

Например:

Git Plugin
Writing Plugin
GitHub Plugin
Godot Plugin
Blender Plugin

Один и тот же Writing Plugin должен работать:

Соруар
Без назначения
детская книга
новый роман

Один и тот же Git Plugin должен работать с любым Git repository.

6.1 Plugin responsibilities

Плагин может предоставлять:

Groups
Items
Actions
Commands
Context Providers
Keybindings
Background jobs
Events
Status indicators

Не каждый плагин обязан реализовывать всё перечисленное.

⸻

7. Groups

Group — стабильная функциональная область внутри Plugin.

Например:

Git
├── Status
├── Branches
├── Changes
├── Commits
└── Stash

или:

GitHub
├── Pull Requests
├── Issues
├── Builds
├── Actions
├── Releases
└── Gists

Группа существует независимо от количества текущих элементов.

Например:

GitHub / Builds

остаётся группой даже при:

0 builds

⸻

8. Items

Item — конкретный объект, предоставленный плагином.

Примеры:

branch feature/auth
PR #127
Issue #84
Build #332
commit e69f...
file architecture.md
note "Hybrid AI"
Blender scene
Godot scene

Core не обязан понимать семантику объекта.

Item принадлежит конкретному Plugin/Group.

⸻

9. Actions

Плагин определяет действия, допустимые для конкретного объекта.

Например:

GitHub / Pull Request
open
checkout
diff
comment
merge
copy-url

Для build:

GitHub / Builds
logs
rerun
cancel
open

Для Git branch:

Git / Branches
checkout
diff
log
merge
delete

Для файла:

Files
open
edit
preview
copy-path

Действия должны быть discoverable через UI.

⸻

10. Plugins are workspace-agnostic

Это обязательное архитектурное ограничение.

Нельзя создавать:

SoruarPlugin
BookwriterPlugin
LightningGamePlugin

если функциональность относится не к самому приложению, а к конкретному проекту.

Правильно:

WritingPlugin
GitPlugin
GodotPlugin
BlenderPlugin

Конкретные данные определяет Workspace.

⸻

11. Workspace

Workspace соответствует конкретному проекту пользователя.

Например:

~/projects/soruar
~/projects/bookwriter.nvim
~/projects/lightning-game

Workspace задаёт:

- project root;
- project metadata;
- project-local configuration;
- набор активных plugins;
- plugin-specific configuration;
- состояние интерфейса;
- локальные overrides.

Workspace не содержит реализацию plugins.

⸻

12. Plugin activation model

Плагины устанавливаются глобально.

Workspace определяет, какие установленные плагины активны для конкретного проекта.

Пример:

Installed globally:
Git ✓
GitHub ✓
Files ✓
Writing ✓
Godot ✓
Blender ✓
AI ✓

Workspace soruar:

Files enabled
Git enabled
Writing enabled
AI enabled
GitHub disabled
Godot disabled
Blender disabled

Workspace lightning-game:

Files enabled
Git enabled
GitHub enabled
Godot enabled
Blender enabled
AI enabled
Writing disabled

⸻

13. Plugin lifecycle

Необходимо различать:

installed
enabled for workspace
enabled for session
available
connected

Пример:

Blender
installed: true
workspace_enabled: true
session_enabled: true
availability: unavailable
reason: blender_not_running

Это не должно считаться ошибкой конфигурации.

⸻

14. Temporary disable

Пользователь должен иметь возможность временно выключить Plugin.

Например:

Disable for session

Эффект:

- Plugin исчезает из текущего интерфейса;
- background jobs останавливаются;
- настройки сохраняются;
- workspace configuration не изменяется;
- после следующего запуска Plugin снова активен.

⸻

15. Persistent disable

Действие:

Disable

означает:

workspace_enabled = false

Плагин остаётся установленным глобально.

Настройки не удаляются.

⸻

16. Uninstall

Удаление Plugin — отдельная операция.

disable != uninstall

Uninstall может удалить:

- plugin package;
- cached resources;

но пользовательские настройки желательно удалять только после отдельного подтверждения.

⸻

17. Plugin discovery

Плагин может сообщать о своей применимости к Workspace.

Пример:

GitPlugin.detect(workspace)

обнаруживает:

.git/

Godot:

project.godot

Writing:

writing.yaml

или другую поддерживаемую структуру.

Результат:

SUPPORTED
UNSUPPORTED
UNKNOWN

Detection не должен автоматически активировать Plugin без пользовательской настройки, кроме явно разрешённых default plugins.

⸻

Пример:

UI должен поддерживать:

- keyboard-only navigation;
- быстрый переход Plugin → Group → Item;
- fuzzy search;
- command palette;
- predictable shortcuts;
- back navigation;
- refresh;
- filtering;
- sorting.

Навигационная модель:

Plugin
↓

↓

↓
Action

20. Command Palette

Должен существовать независимый от текущего экрана command interface.

Пример:

> git checkout
> github pr
> plugin disable
> workspace switch
> build logs

Плагины могут регистрировать свои команды.

Например:

github.pr.open
github.build.logs
git.branch.checkout
writing.search

⸻

21. Custom Plugins

Пользователь должен иметь возможность устанавливать собственные плагины.

Это является P0 архитектурным требованием, даже если полноценный public SDK появится позже.

Первая версия Core не должна иметь привилегированный внутренний API для встроенных интеграций.

First-party plugins и third-party plugins должны использовать максимально близкий plugin contract.

⸻

22. Plugin package

Минимальная структура:

my-plugin/
├── plugin.yaml
├── plugin executable/module
└── README.md

Manifest:

api_version: 1
default_enabled: true
permissions:

- network.github.com
- process.git

23. Plugin API — conceptual contract

Минимальный интерфейс:

Plugin
│
├── metadata()
├── detect(workspace)
├── activate(context)
├── deactivate()
│
├── groups()
├── load(group)
│
├── actions(item)
├── execute(action, item)
│
├── commands()
│
└── status()

Дополнительные extension points:

provide_context()
subscribe_events()
background_refresh()
register_keybindings()

24. Workspace context

При активации Plugin получает WorkspaceContext.

Например:

WorkspaceContext
root
workspace_id
config
environment
session
permissions
event_bus

Плагин использует его как окружение исполнения.

Plugin остаётся workspace-agnostic.

⸻

25. Configuration precedence

Настройки желательно применять в следующем порядке:

Plugin defaults
↓
Global user config
↓
Workspace config
↓
Session overrides

То есть:

session > workspace > global > defaults

Session override не сохраняется после завершения сессии.

⸻

26. Permissions

Custom plugins нельзя автоматически считать доверенными.

Plugin manifest должен декларировать capabilities.

Например:

permissions:
filesystem:
read: workspace
write: workspace
network: - api.github.com
process: - git

Core принимает решение о выдаче разрешений.

Plugin не должен иметь неограниченный доступ только потому, что он установлен.

⸻

27. AI

AI не является центральной сущностью продукта.

Это либо:

AI Plugin

либо capability, предоставляющая действия другим plugins.

Например:

GitHub / PR #42
Open
Diff
Checkout
Review with AI
Explain with AI

или:

Files / architecture.md
Open
Edit
Diff
Ask AI

Terminal Workspace должен быть полезен без AI.

Это важное продуктовое требование.

⸻

28. AI context integration

Plugin может предоставлять структурированный контекст:

provide_context(item)

Например GitHub PR:

{
"repository": "...",
"title": "...",
"description": "...",
"diff": "...",
"comments": "...",
"checks": "..."
}

AI Plugin может использовать этот контекст без необходимости понимать внутреннюю реализацию GitHub Plugin.

Это позволяет позже подключить:

- облачные модели;
- локальные модели;
- Hybrid AI;
- agent runtimes.

Но эти возможности не должны усложнять MVP терминала.

⸻

29. Events

Core должен иметь простой event bus.

Примеры:

workspace.opened
workspace.closed
plugin.enabled
plugin.disabled
item.selected
item.updated
action.started
action.completed
action.failed

Плагины могут подписываться на события, если получили соответствующее разрешение.

⸻

30. Refresh model

Не все источники требуют одинаковой частоты обновления.

Plugin сам объявляет стратегию:

manual
on_focus
interval
event_driven

Например:

Git:

on_focus

CI:

interval: 30s

Filesystem:

event_driven

⸻

31. Error handling

Ошибка одного Plugin не должна ломать Workspace.

Например:

GitHub ⚠ authentication required
Blender ○ unavailable
Git ✓ ready
Files ✓ ready

Plugin crash должен быть изолирован Core.

⸻

32. MVP

MVP должен проверить основную продуктовую гипотезу:

Можно ли существенно сократить ежедневное переключение между приложениями, перенеся наиболее частые рабочие источники информации и действия в TUI?

P0 Core

Необходимо реализовать:

- terminal UI;
- workspace open/switch;
- Plugin API;
- plugin discovery/loading;
- global plugin installation concept;
- workspace plugin activation;
- temporary session disable;
- persistent workspace disable;
- Groups;
- Items;
- Actions;
- command palette;
- keyboard navigation;
- plugin configuration;
- basic permissions;
- plugin error isolation.

Writing

├── Notes
├── Characters
├── Locations

35. Non-goals for MVP

Не реализовывать в первой версии:

- собственную task management system;
- сложный AI orchestration;
- встроенный RAG;
- universal WorkItem abstraction;
- автоматическое объединение сущностей разных plugins;
- graphical UI;
- plugin marketplace;
- cloud synchronization;
- distributed agents;
- collaborative workspace;
- сложные dashboards;
- dynamic AI-generated tabs.

Это не требуется для проверки основной гипотезы продукта.

⸻

36. UX requirement: no forced abstraction

GitHub PR должен оставаться GitHub PR.

Git branch — branch.

Markdown note — note.

Нельзя заставлять все источники превращаться в:

WorkItem
Task
Resource
Entity

только ради архитектурной симметрии.

Core может иметь технические интерфейсы Item, но пользовательская семантика должна оставаться нативной для Plugin.

⸻

37. Performance requirements

TUI должен ощущаться мгновенным.

Целевые значения MVP:

startup:
< 300 ms без сетевых plugins
local group open:
< 100 ms
navigation:
< 16–50 ms perceived latency
network groups:
show cached state immediately,
refresh asynchronously

Медленная сеть не должна блокировать весь интерфейс.

⸻

38. Offline behavior

Workspace должен продолжать работать без сети.

Например:

Git available
Files available
Writing available
GitHub offline

Network Plugin показывает сохранённое состояние или понятный offline state.

⸻

39. Persistence

Core хранит:

installed plugins
global plugin config
known workspaces
workspace plugin activation
workspace layout
workspace-specific plugin config
recent workspaces

Session-only state хранится отдельно и не должен автоматически становиться постоянным.

⸻

40. Security boundary

Особое внимание custom plugins.

Core должен контролировать:

- filesystem;
- process execution;
- network access;
- credentials;
- environment variables.

В перспективе Plugin runtime желательно сделать изолируемым, чтобы plugin crash или malicious plugin не получал автоматически полный доступ к машине.

Для MVP допустима более простая реализация, но permission model должен присутствовать в архитектуре с первого дня.

43. Acceptance criteria for MVP

MVP считается успешным, если выполняются следующие условия.

1. Пользователь может открыть arbitrary local project как Workspace.
2. Plugin может быть установлен независимо от Workspace.
3. Workspace может выбирать собственный набор активных plugins.
4. Один Plugin работает с несколькими Workspaces без project-specific code.
5. Plugin можно:

enable
disable
disable for session

6. Plugin может предоставить минимум:

Group
Item
Action

7. Custom Plugin использует тот же основной API, что и first-party plugins.
8. Ошибка Plugin не завершает приложение.
9. Пользователь способен выполнить типичный flow:

launch
→ plugin
→ group
→ item
→ action

без мыши.

10. Git/GitHub/Files workflow оказывается быстрее субъективно и по количеству переходов, чем открытие соответствующих отдельных приложений.

44. Основные архитектурные принципы

Principle 1 — Terminal first

Продукт проектируется вокруг терминальной работы, а не как GUI, перенесённый в TUI.

Principle 2 — Plugin first

Вся domain-specific функциональность находится в Plugins.

Principle 3 — Workspace is project

Workspace соответствует реальному проекту пользователя.

Principle 4 — Plugins are workspace-agnostic

Plugin реализует capability, а не конкретный проект.

Principle 5 — Workspace selects capabilities

Workspace определяет набор активных Plugins.

Principle 6 — Native semantics

PR остаётся PR, branch остаётся branch, note остаётся note.

Principle 7 — AI is optional

AI расширяет действия, но не является причиной существования продукта.

Principle 8 — Extensibility from day one

Custom plugins являются частью архитектуры MVP, а не будущей надстройкой.

Principle 9 — Information before automation

Сначала продукт упрощает доступ к информации и простым действиям. Автономные агенты можно добавить позже.

Principle 10 — Minimal Core

Если функциональность можно реализовать Plugin’ом, она не должна находиться в Core.

45. Краткая формула продукта

Terminal Workspace — это минимальное TUI-ядро для работы с проектами, где повседневные источники информации и действия подключаются через workspace-agnostic плагины.

Project
↓
Workspace
↓
Active Plugins
↓
Groups
↓
Items
↓
Actions

Пользователь устанавливает Plugins один раз, выбирает необходимые для каждого Workspace и получает быстрый терминальный доступ к рабочему контексту без постоянного переключения между приложениями.
