# Project-local конфигурация и Core-команды

Статус: локальное решение реализации этапа 1 roadmap, не исходное продуктовое требование.

Конфигурация хранится в `.terminal-workspace.json` в корне проекта. Выбран JSON и `serde_json = 1.0.108`, доступный в локальном offline-кэше и совместимый с текущим Rust toolchain. Это заменяемый формат; версия файла (`version: 1`) отделена от версии исходного Plugin API.

```json
{
  "version": 1,
  "plugins": {
    "files": {
      "enabled": true,
      "permissions": ["WorkspaceRead"],
      "settings": {}
    }
  },
  "overrides": {}
}
```

`enabled` — активация для Workspace. Session suspend хранится только в памяти. Повторное enable включает Workspace и текущую сессию. Installation остаётся отдельной: записи файла не устанавливают и не включают отсутствующий пакет. В этом прототипе доступные реализации по-прежнему связываются при сборке. Фоновых задач и lifecycle hooks пока нет; suspend запрещает новые обращения через App и очищает отображаемые данные, но не изолирует код и не останавливает произвольные потоки стороннего плагина.

Файл читается при `App::open`; `App::new` оставлен для явно непостоянных сессий и тестов. Приложение разрешает Files как default и выдаёт WorkspaceRead только при отсутствии сохранённого решения о разрешениях. Пустой массив permissions означает явный отказ, который default после перезапуска не отменяет. Для других реализаций defaults задаёт вызывающий код; discovery сам не включает плагин.

`settings` принадлежит плагину и доступен через `Workspace::plugin_settings`. Core сохраняет объект без интерпретации. Custom Catalog читает настройку `greeting` и проверяется в двух проектах. `overrides` сохраняется как объект; применение keybinding overrides относится к этапу 2. Настройки редактируются вручную при закрытом приложении, отдельный редактор настроек ещё не реализован. Секреты в этот файл не записываются приложением.

Сохраняются неизвестные записи плагинов, поля, permissions и overrides. Неизвестные permissions не выдаются. Некорректный JSON, неподдерживаемая версия, неверные типы, файл больше 1 MiB и symlink дают видимую ошибку: сессия открывается с отключёнными плагинами, default-разрешения не выдаются, запись блокируется до исправления файла и перезапуска. Неизвестные поля допускаются для расширения схемы; несовместимые форматы требуют новой версии.

Сохранение использует соседний временный файл, `create_new`, `sync_all` и rename. Состояние App меняется только после успешной записи. Перед записью сравниваются байты с загруженной версией; обнаруженное внешнее изменение не перезаписывается. Это не межпроцессная блокировка: одновременные записи между проверкой и rename всё ещё возможны. Синхронизация родительского каталога и полная гарантия при внезапном отключении питания не реализованы.

Единый registry содержит Core и plugin commands. Namespace `core` зарезервирован. Core-команды доступны без активного плагина и выбранного Item; целевой plugin id передаётся через `CommandInvocation.args`. API v0.2 добавляет args и делает `App::invoke` изменяющим состояние (`&mut self`); disable и suspend теперь возвращают Result. Plugin::execute сохраняет прежний контракт. Командная строка, палитра, bindings и действия на вкладке плагина вызывают те же CommandId.

Для прототипа выбрана leader-клавиша `,`: `, e/d/s` — enable/disable/suspend; `, p` — список состояний; `, g/r` — grant/revoke WorkspaceRead. Это изменяемые defaults, не утверждённый продуктовый контракт. В палитре и contextual Actions цель по умолчанию — выбранная вкладка плагина; явный аргумент `:command plugin-id` имеет приоритет. Состояние активации и разрешения просматриваются отдельно: active не обещает доступность данных, подключение или enforcement изоляции.

Проверки покрывают restart, два проекта, suspend без записи, отзыв разрешений без повторной default-выдачи, сохранность неизвестных данных, ошибки чтения/сохранения, конфликт внешнего редактирования, custom plugin и четыре пути вызова из TUI. PTY проверяет отключение/включение и отзыв/выдачу разрешения после перезапуска. Performance-цели MVP этим этапом не подтверждаются.

Продолжение: [этап 2](0004-workspace-switching-and-bindings.md) реализует переключение Workspace, применение `overrides.keybindings` и API v0.3. Ограничения выше описывают состояние этапа 1; актуальный контракт — в `docs/plugin-api.md`.

Последующее решение: [этап 3 — executable packages и Plugin API 0.4](0006-executable-plugin-runtime.md) добавляет глобальную установку, lifecycle и расширенную permission model. Ограничения статической загрузки в этом документе описывают состояние на момент исходного решения.
