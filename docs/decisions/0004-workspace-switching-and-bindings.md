# Переключение Workspace и контекстный ввод

Статус: локальное решение реализации этапа 2 roadmap. Опускать namespace активного плагина — принятое пользователем UX-решение; конкретные клавиши, JSON-схема overrides и Rust-контракты ниже — изменяемые решения прототипа.

## Переключение

`core.workspace.open` принимает один путь, включая пробелы; относительный путь разрешается от корня текущего Workspace. `core.workspace.previous` возвращает к предыдущему проекту; повторный вызов переключает между последними двумя. Обе команды входят в общий CommandRegistry. Из палитры, binding или Action команда открытия без пути переводит UI в строку `:core.workspace.open ` для ввода аргумента. App без аргумента возвращает ошибку, а не выбирает проект самостоятельно.

Defaults Core: `, w` открывает проект, `, b` возвращает к предыдущему. Команды доступны и при отсутствии активных или установленных плагинов. На вкладках плагинов `a` показывает также Core Actions переключения.

App сохраняет установленные реализации и registry при переключении; код плагина не принадлежит проекту. Перед заменой контекста проверяется каталог, читается project-local конфигурация и сохраняются недостающие явно объявленные application defaults. Ошибка пути, конфигурации или сохранения оставляет текущий Workspace и его разрешения действующими. Повреждённая конфигурация нового проекта отклоняет переход; начальный запуск сохраняет fail-closed поведение этапа 1.

Активация и выданные разрешения рассчитываются заново из конфигурации нового проекта. Saved permission denial не отменяется default. Settings и overrides передаются из нового Workspace. Временное отключение хранится отдельно для каждого канонического корня до выхода из приложения: смена проекта не возобновляет отключённый в нём плагин. `App::new` остаётся непостоянным; его настройки для посещённых проектов сохраняются только в памяти.

UI запоминает вкладку плагина, группу, opaque location, фокус, выбор, фильтр и порядок для каждого проекта в текущей сессии. При возврате данные загружаются заново через Plugin API. Items, Blocks, Actions и незавершённый ввод из другого проекта не переносятся. Недоступная сохранённая локация даёт ошибку и возврат к корневому представлению; отозванные разрешения проверяются заново. Состояние UI не сохраняется между запусками. Lifecycle hooks и отмена фоновых задач относятся к последующим этапам; работающих фоновых задач здесь ещё нет.

## Bindings

API v0.3 добавляет необязательный `Plugin::keybindings() -> Vec<KeyBinding>`. Binding задаёт последовательность символов, CommandId и `BindingScope`: Plugin, Group или View (group + opaque location). Global используется Core. Плагин объявляет только собственные команды и собственный namespace; ошибочное объявление или panic не устанавливает частично зарегистрированный плагин.

В обычном режиме применяются bindings текущего активного плагина, группы и представления. Более узкая область имеет приоритет для одинаковой последовательности; явный project-local override имеет приоритет перед defaults, а среди overrides также побеждает более узкая область. При отключении плагина локальные bindings пропадают, Core остаётся доступен. Permissions проверяются в общем маршруте исполнения.

Поддерживаются последовательности произвольной длины из печатных символов без пробелов, включая Unicode. Esc отменяет последовательность; другая несимвольная клавиша также отменяет её. Неверное продолжение даёт ошибку и сбрасывает последовательность. Statusline показывает допустимые продолжения и CommandId; `?` показывает эффективные bindings текущего контекста и ошибки конфигурации. В поиске, палитре и командной строке символы вводят текст. Timeout и модификаторы в объявлениях bindings пока не поддерживаются.

Начальные `q h j k l r s a : / ?`, Space и управляющие клавиши зарезервированы для ввода и навигации UI. Начальная `,` зарезервирована для Core. Эти ограничения и leader — решения текущей реализации. На момент этапа 2 defaults Files были `p` preview, `y` path, `o` open, `u` parent, с локальными aliases `fp/fs/fo/fu`. [Итерация 2.1](0005-keyboard-defaults.md) оставляет только `p` и общую навигацию; глобальный вызов неактивного плагина по namespace пока отсутствует. UI больше не содержит Files-специфичного списка сочетаний.

Два объявления одной последовательности в одной области и пара «полная последовательность / её продолжение» считаются неоднозначными. Конфликтующие bindings не исполняются; диагностика доступна сразу после загрузки через App и UI, остальные команды работают. Для полной последовательности, являющейся префиксом другой, не введён неявный timeout или выбор случайного победителя.

## Project-local overrides

Существующий JSON version 1 расширяется опциональным массивом `overrides.keybindings`:

```json
{
  "version": 1,
  "plugins": {},
  "overrides": {
    "keybindings": [
      {"keys": "p", "plugin": "files", "command": null},
      {"keys": "vnp", "plugin": "files", "command": "files.preview"},
      {"keys": "v", "plugin": "files", "group": "entries", "location": "notes", "command": "files.path"},
      {"keys": ",o", "command": "core.workspace.open"}
    ]
  }
}
```

Без plugin область Global и допустимы только Core-команды. Plugin задаёт локальную область; group уточняет группу; location требует group и задаёт представление. `command: null` отключает binding в указанном контексте, включая унаследованный из более широкой области. Чтобы заменить клавишу, отключи старую и добавь новую. Аргументы и Item берутся из текущего контекста тем же способом, что для палитры; override не задаёт отдельную бизнес-логику.

Некорректные записи и неизвестные CommandId показываются как ошибки bindings; конфигурация сохраняется без удаления неизвестных данных и остальные bindings продолжают работать. Повторный override одной последовательности в одной области отключает её и сообщает конфликт. Settings и overrides редактируются вручную; изменённый файл читается при следующем открытии проекта или перезапуске. Открытие уже текущего канонического корня сохраняет текущую сессию без перечитывания файла.

Проверки: два проекта в одном App, независимые permissions/settings/activation, временное отключение при возврате, ошибки открытия и сохранения defaults; четыре UI-маршрута открытия и исполнения; вложенные локации, свежие данные и устаревшие локации; scoped overrides, Unicode, отмена, конфликты и ввод текста; независимо упакованный Catalog с bindings Plugin/Group/View. Реальный Unix PTY проверяет переключение, пробелы в пути, overrides, восстановление контекста и терминала. Полные performance-цели MVP этим этапом не подтверждаются.

PTY smoke check от 4 октября 2026 на macOS, `target/debug/tw`, временный локальный проект с Files и первичным сохранением defaults: от запуска процесса до первого кадра 631.8 ms; открытие каталога 4.6 ms; возврат к родителю 3.7 ms. Это единичный замер по методике `tests/tui_pty.py`, а не release benchmark или распределение задержек. Startup в этих условиях превышает цель < 300 ms; цель остаётся непроверенной для release-сборки и требует отдельной работы этапа 7.
